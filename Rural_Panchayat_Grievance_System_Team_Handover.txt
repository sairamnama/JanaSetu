2. PROJECT OVERVIEW
======================================================================

Project title:
Web-Based Rural Panchayat Grievance Management System

Purpose:
Help rural citizens report public-service problems, track progress, and
confirm whether those problems have actually been fixed. Panchayat admins
review complaints and assign suitable local workers. Workers update progress
and submit evidence. The admin and original citizen verify the result before
the grievance is closed.

Examples of grievances:
- Damaged roads
- Water-supply problems
- Drainage and sewage issues
- Garbage collection and sanitation
- Broken streetlights
- Electricity-related local issues
- Other local public-service problems supported by the Panchayat

The website should be easy for people with limited technical knowledge.
The Citizen and Worker portals are intended to support both English and
Telugu, with a simple, mobile-friendly interface.

The main problem being addressed:
In a manual complaint process, citizens may not receive a tracking number,
may not know who is responsible, and may have to visit the Panchayat office
repeatedly. A complaint may also be marked fixed without checking with the
citizen. This system aims to make each step traceable.

4. THE THREE PORTALS
======================================================================

A. CITIZEN PORTAL
Purpose: Citizens submit public-service complaints and track their own cases.

Navigation:
1. Home
2. Submit Grievance
3. Track Grievance

Home:
- Simple welcome message and explanation.
- Clear buttons to submit or track a grievance.

Submit Grievance:
Planned fields include title, description, category, village/ward or location,
landmark, and a photo/attachment if supported by the existing application.
The system validates required fields, saves the grievance, generates a
unique Grievance ID, and displays a confirmation.

Track Grievance:
- Show only the logged-in citizen's private grievances.
- Display Grievance ID, title, date, category, location, status, and progress.
- Explain status labels in plain language.
- Show verification outcomes and requests for feedback when relevant.
- Never expose another citizen's private information.

Language:
The login page should offer English and Telugu. Selecting Telugu should
translate the entire Citizen Portal, including navigation, forms, buttons,
validation errors, status labels, confirmations, and messages. Preserve the
selected language across navigation and refresh.

B. WORKER PORTAL
Purpose: Workers see assigned jobs, accept or reject them, report progress,
and submit evidence.

Navigation:
1. Home
2. Work
3. Work Proof & Report

Planned worker registration/profile fields:
- Full name
- Unique Worker ID
- Mobile number
- Work type/skill (Electrician, Plumber, Mechanic, Mason, Sanitation Worker,
  Water Supply Worker, or Other)
- Experience in years
- Authentication information required by the secure login design

Worker Home/Profile should show actual saved values: name, Worker ID, mobile,
work type, experience, active/inactive status, Loyalty Points, rating if
implemented, and relevant work history.

Work:
- Show only assignments belonging to the logged-in worker.
- Show grievance details, location, category, assignment date, and status.
- Provide Accept and Reject actions.
- Require a reason for rejection.
- Accepted work should appear as an active task.
- Rejected work should be recorded and reported to the admin for reassignment.

Work Proof & Report:
- Update work progress.
- Submit a completion description and time.
- Upload photo evidence if supported.
- Report inability to complete work and explain the reason or resources/help
  required.
- Store reports against the correct grievance and assignment.

The Worker login page should offer English and Telugu, and the selected
language should apply throughout the Worker Portal.

C. PANCHAYAT / ADMIN PORTAL
Purpose: Authorized administrators manage grievances and workers.

Navigation:
1. Home
2. Solve Grievances
3. Workers

Admin Home:
Show real database-backed counts for submitted, pending, assigned, in
progress, awaiting verification, resolved, and overdue grievances where
those states exist. Do not use hard-coded or fake statistics.

Solve Grievances:
- Review grievance details and history.
- Assign the grievance to an eligible worker.
- Monitor acceptance, rejection, and progress.
- Review worker completion evidence.
- Record citizen verification.
- Request rework, reopen, reassign, or escalate where rules permit.

Workers:
- View registered workers.
- Activate/deactivate workers, if authorized and implemented.
- View skills, experience, workload, points, and rating where available.
- View Loyalty Points history.
- Make manual points adjustments only with authorization and a mandatory
  reason.

Admin security:
Only authorized administrators can access admin functions. Typing “Admin”
or selecting an Admin role must never grant access. Admin registration must
not be publicly available unless a controlled authorization process exists.

5. COMPLETE GRIEVANCE WORKFLOW
======================================================================

Step 1 — Citizen submits a grievance.
The citizen logs in, enters the problem details, chooses a category and
location, adds an attachment if supported, and submits the form.

Step 2 — System saves it.
The backend validates and saves the data, creates a unique Grievance ID,
sets an initial status such as SUBMITTED, and shows a confirmation.

Step 3 — Admin reviews it.
The grievance appears in the admin portal. The admin checks the details and
decides which skill or department is needed.

Step 4 — Admin assigns a suitable worker.
The system should help identify workers whose skill matches, whose account
is active/approved, whose points meet the configurable minimum (example:
60), and whose workload allows another job. Loyalty Points must not be the
only eligibility factor.

Step 5 — Worker accepts or rejects.
The worker sees the assignment. Acceptance moves it forward. Rejection
requires a reason, informs the admin, and releases the task for reassignment.
A default -5 Loyalty Points penalty has been specified for rejection; it
must be configurable and recorded exactly once per valid rejection.

Step 6 — Worker performs the work.
The worker updates progress. If unable to finish, the worker reports why and
what help or resources are required.

Step 7 — Worker submits a completion report.
The worker describes the work and provides evidence, such as photographs
where supported. Uploading proof must not automatically close the grievance.

Step 8 — Admin checks the evidence.
The admin reviews the report and proof. If the proof is insufficient, the
admin may request more information or rework.

Step 9 — Original citizen verifies the result.
The planned options are:
- YES: the citizen confirms the problem is fixed.
- PARTIALLY: some work was done but the problem remains partly unresolved.
- NO: the citizen says the problem is not fixed.

The project includes a “double grievance”/double-verification idea because
worker-submitted proof may not be enough. The admin should review evidence
and contact the original citizen for confirmation. Record the result, time,
and method.

Step 10 — System decides the outcome.
- YES, after required admin review: mark verified/resolved and close.
- PARTIALLY: send back for more work or review.
- NO: reopen or request rework.
- No response: do not treat silence as YES or NO automatically. Keep pending,
  retry verification, or escalate according to a defined policy.

Step 11 — Preserve history.
Citizens see the latest status, workers see their own assignment history,
and admins can inspect the full case history. Record who performed each
important action and when.

6. LOYALTY POINTS
======================================================================

Loyalty Points represent worker reliability/performance and are separate
from a public star rating.

Requirements:
- Store the current balance in the database.
- Record every change in a transaction history.
- A transaction should contain Worker ID, previous balance, change amount,
  new balance, reason, timestamp, and authorized actor/source.
- Make initial points and rules configurable.
- Admins can view balances and history.
- Manual adjustments require admin authorization and a reason.
- Workers cannot change their own points.
- Prevent repeated requests from deducting points more than once.
- Use safe database updates to avoid corrupting balances during concurrent
  operations.

Scoring events discussed include rejected assignments (-5 by default),
verified work quality, citizen satisfaction, and reliability. Do not add
automatic score changes without a documented rule. The minimum eligibility
threshold (example 60) must be configurable, not copied as a hard-coded
condition in many files.

7. STATUSES AND HISTORY
======================================================================

The team must use one consistent status model across the database, backend,
API, and UI. A possible detailed lifecycle is:

SUBMITTED -> UNDER_REVIEW -> APPROVED -> ASSIGNED -> IN_PROGRESS ->
WORK_COMPLETED -> OFFICER_VERIFICATION -> CITIZEN_VERIFICATION ->
VERIFIED -> RESOLVED -> CLOSED

Alternative outcomes may include REJECTED, REWORK_REQUIRED, REOPENED,
ESCALATED, and CANCELLED where approved by the project rules.

This is a proposed lifecycle, not proof that every status exists in code.
Define which role can make each transition. The backend must reject invalid
transitions. Preserve history when cases are reopened or reassigned.
Translate status labels into English and Telugu.

16. ONE-MINUTE PROJECT EXPLANATION
======================================================================

"We are building a website for rural Panchayat grievance management. A
citizen can report a local problem such as a damaged road, water issue, or
broken streetlight and receive a Grievance ID to track it. The Panchayat

not fixed, the grievance can return for more work instead of being closed
incorrectly. The system has three portals: Citizen, Worker, and Admin.
Citizen and Worker portals are intended to support English and Telugu. We
are building and testing the project step by step in Antigravity IDE. We
must verify the actual code, database, security, and deployment before
